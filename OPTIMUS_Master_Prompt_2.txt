4. CHANGE #1 — MOVEMENT MUST USE THE CURRENT FRAME OF REFERENCE
======================================================================

This is an explicit gameplay rule change.

The current movement must NOT remain tied to the player's initial/spawn/world reference frame.

Ordinary movement must always be interpreted from the player's CURRENT state:

- current gravity vector
- current local-up vector
- current camera direction
- current tangent movement plane

The mental model must be:

    "W means move forward from where I am NOW."

NOT:

    "W means move in the direction that was forward when the race started."

Example:

1. Player starts on the normal floor.
2. W moves forward normally.
3. Player turns gravity onto the right wall.
4. That wall becomes the player's current floor.
5. W/A/S/D now operate naturally on that wall.
6. Space/jump acts relative to current gravity/local up.
7. Player moves to the ceiling.
8. Movement immediately uses the ceiling as the current local plane.
9. Chained shifts must remain intuitive.

Implementation principle:

    local_up = -current_gravity.normalized()

Then:
- derive camera forward and right
- project them onto the plane perpendicular to current gravity
- safely normalize
- use them as current forward/right movement axes
- handle the degenerate case where camera forward approaches parallel with local_up
- preserve orientation continuity after shifts
- preserve camera-relative Gravity Move commands
- preserve quaternion/basis orientation logic
- never turn this into Euler-angle orientation logic
- never use Vector3.UP as permanent player-up in gravity-relative logic
- do not store spawn orientation as the permanent movement basis

The camera transition must remain smooth enough that correct movement does not feel disorienting.

This rule must work for all six gravity orientations and after repeated chained shifts.

Add/extend regression coverage for:
- floor
- all four wall orientations
- ceiling
- repeated shifts
- forward/right after multiple shifts
- current-state camera-relative movement
- jump/current-local-up behavior where applicable
- online remote orientation presentation

Bots must still obey the same physical movement model where relevant.

5. CHANGE #2 — PROCEDURAL CAVE MUST FEEL LIKE A CAVE, NOT A HOUSE
======================================================================

The current procedural generation functions and architecture are broadly valuable.
Do NOT throw away the generator unless absolutely necessary.

The problem is mainly the resulting SPATIAL STRUCTURE and VISUAL FEEL.

Current issue:
- too room-like
- too rectangular
- too much like a house/building
- spaces often feel overly broad
- junction rhythm is not cave-like enough

New target:
- narrow
- long
- winding
- layered
- corridor-first
- vertically varied
- intentionally confusing but fair
- recognisably cave-like

The player should feel as though they are navigating a long underground tunnel network.

----------------------------------------------------------------------
5.1 CORRIDOR-FIRST TOPOLOGY
----------------------------------------------------------------------

Bias generation toward:

- long straight tunnel runs
- long L-shaped chains
- narrow turns
- T-junctions
- cross-junctions
- narrow branches
- vertical shafts
- ramps / stepped slopes
- upper tunnels
- lower tunnels
- reconnecting routes
- occasional compact chambers
- dead ends
- real cycles

Reduce:
- repeated large rectangular rooms
- house-like hallways
- wide open box spaces
- one-room-per-node presentation
- building-floor visual rhythm

Chambers should be occasional special spaces, not the default shape.

Desired rhythm:

    narrow tunnel
        ->
    long passage
        ->
    junction
        ->
    branch / climb / descent
        ->
    long passage
        ->
    loop / dead end / reconnect
        ->
    further cave

----------------------------------------------------------------------
5.2 NARROWER SPACE
----------------------------------------------------------------------

The cave must be noticeably narrower than the Prompt-1 version.

But do this safely.

Inspect:
- player capsule/collision
- camera radius/near clip
- bot navigation
- gravity shifts
- wall walking
- hazards
- online remote racers

Choose a tunnel cross-section that feels tight without causing:
- camera clipping
- physics jitter
- stuck players
- impossible passing
- unfair multiplayer blocking

A useful design target is approximately 1.8x–2.5x player collision diameter for ordinary passages, adjusted to the actual rig.

Junctions can widen modestly.
Chambers can be larger.
Do not make the default corridor feel like a room.

Make important sizes tunable rather than scattering magic numbers.

----------------------------------------------------------------------
5.3 LONGER PASSAGES
----------------------------------------------------------------------

Increase average travel distance between meaningful junctions.

Do not reveal a room/junction every few steps.

Tune:
- minimum corridor run length
- preferred run length
- max run before a forced turn/junction
- branch spacing
- shaft spacing
- vertical transition spacing

Use controlled variation.

The player should occasionally commit to a long path and only later discover:
- another junction
- a dead end
- a loop back
- an upper/lower route

----------------------------------------------------------------------
5.4 REAL LOOPS / RETURNING TO THE SAME PLACE
----------------------------------------------------------------------

Intentional loops are REQUIRED.

The player should sometimes travel through multiple distinct cave segments and eventually return to a place they recognise.

This is intended to:
- increase race tension
- create uncertainty
- reward memory
- make landmarks meaningful
- punish careless exploration without being unfair

IMPORTANT:
The user's phrase "self loop" means a gameplay loop/cycle in the cave.

Do NOT fake this using a graph edge from a node directly to itself.

Implement true graph cycles:
- branch reconnects to an earlier node/region
- alternate route returns to an earlier corridor
- upper route reconnects to a lower/earlier route
- multi-turn loop comes back to a recognisable location

Loops should include enough travel that returning feels meaningful.

Do not make every branch reconnect.
Balance cycles with progression and dead ends.

----------------------------------------------------------------------
5.5 DEAD ENDS
----------------------------------------------------------------------

Dead ends are REQUIRED.

They should:
- create exploration risk
- create race pressure
- encourage backtracking
- sometimes reward curiosity
- vary in length

Possible dead-end contents:
- mystery box
- clue chance
- hazard
- landmark
- environmental detail
- nothing

Do not make nearly every branch a dead end.

Bots must recognise dead ends and backtrack without infinite cycling.

----------------------------------------------------------------------
5.6 BOTH UPPER AND LOWER CAVE ROUTES
----------------------------------------------------------------------

The cave must NOT behave like:

    start low -> climb upward -> finish high

Verticality must move BOTH directions.

Require representative seeds to contain:
- upward climbs
- downward descents
- vertical shafts
- descending ramps/tunnels
- ascending ramps/tunnels
- lower branches
- upper branches
- routes that climb and later descend
- routes that descend and later climb
- loops reconnecting different elevations

Example feeling:

    start
      ->
    long tunnel
      ->
    junction
      ->
    descend
      ->
    lower cave
      ->
    dead end / loop
      ->
    shaft upward
      ->
    high tunnel
      ->
    drop downward
      ->
    junction
      ->
    finish

The cave should be a layered 3D network, not a staircase toward the finish.

6. CHANGE #3 — FINAL DESTINATION NOW QUALIFIES PLAYERS FOR A FINAL DUEL
======================================================================

This is the largest game-flow change.

OLD Prompt-1 rule:
    first racer reaching the hidden finish wins.

NEW Prompt-2 rule:
    first TWO racers reaching the hidden finish qualify for a final battle.
    The battle decides Champion.

The final battle is:

    THE FREEDOM DUEL

The cave race now determines:
- who qualifies
- qualification order
- starting mobility advantage
- later placement order

The Freedom Duel determines:
- Champion
- 2nd place

----------------------------------------------------------------------
6.1 QUALIFICATION / WAITING FLOW
----------------------------------------------------------------------

First cave finisher:
- becomes Finalist A
- receives "QUALIFIED 1ST" / equivalent feedback
- does NOT immediately become Champion
- enters a safe finalist waiting state / winning lobby / staging state
- cannot be damaged by unfinished cave hazards while waiting
- cannot unfairly damage the future second finalist before the duel begins

Second cave finisher:
- becomes Finalist B
- receives "QUALIFIED 2ND"
- triggers the transition into the Freedom Duel

The duel starts only after both finalists are ready.

Other racers:
- preserve their cave placement progress
- players finishing after the first two become spectators of the Freedom Duel
- eliminated racers may also spectate
- preserve 3rd/4th/5th and elimination/DNF information

If architecture supports racers still finishing while the duel begins cleanly:
- allow it
- move them to spectator mode when they later finish

If that creates unstable cross-world concurrency:
- use a clean transition rule that preserves 3rd–5th ordering
- do NOT build a fragile concurrency system merely for spectacle

Never soft-lock waiting forever for finalist #2.

Fallbacks:
- if only one racer can possibly remain/qualify because all others are eliminated/disconnected, that qualifier wins by default
- in a two-racer match, if racer #2 is eliminated before qualifying, racer #1 wins by default
- use a reasonable timeout/fallback only if needed to guarantee resolution

----------------------------------------------------------------------
6.2 FIRST FINISHER EARNS MORE DEGREE OF FREEDOM
----------------------------------------------------------------------

The cave-race reward must be thematic.

Preferred duel start:

FINALIST A — 1st cave finisher:
- starts with 3DOF movement
- free ground-plane movement
- vertical freedom through jump and/or controlled air dash
- can exploit elevated routes immediately

FINALIST B — 2nd cave finisher:
- starts with 2DOF movement
- ground-plane movement
- no normal vertical jump at duel start

Do NOT permanently limit Finalist B to 1DOF.

1DOF may exist only as a short temporary debuff.

To prevent the first finisher advantage from becoming an automatic victory:
give Finalist B ONE modest compensation, preferably:
- a single opening shield / one-hit shield

Alternative compensation is allowed only if it is similarly small and defensive.

Do NOT give the second finisher a huge damage advantage.

The first finisher should feel rewarded mainly through FREEDOM/MOBILITY.

----------------------------------------------------------------------
6.3 DUEL MOVEMENT DEFINITIONS
----------------------------------------------------------------------

Make DOF understandable in actual control terms.

Suggested interpretation:

2DOF:
- movement along two arena tangent axes
- no normal jump / no free vertical traversal

3DOF:
- same ground movement
- plus vertical freedom through jump / controlled air dash / equivalent
- access to elevated routes

Temporary 1DOF:
- one meaningful movement axis remains
- short duration only
- must not fully remove aiming/firing unless intentionally designed
- clear feedback

Do not pretend spatial 4D exists.
If a fully free 3DOF player receives another Freedom Core, grant a temporary ability rather than calling it literal 4DOF.

Examples:
- air dash recharge
- brief shield
- mobility burst

----------------------------------------------------------------------
6.4 NO CAVE "MOVE" RESOURCE IN THE DUEL
----------------------------------------------------------------------

The five cave Gravity Move charges do NOT function as the duel movement resource.

Inside the Freedom Duel:
- no cave Move consumption
- no normal cave G+WASD/G+Space resource loop
- no dependence on remaining cave Move count
- both finalists receive the duel's own DOF state

This separates:
- cave exploration freedom
from
- combat freedom

Do not accidentally carry a player's depleted cave Move count into the duel as a combat disadvantage.

----------------------------------------------------------------------
6.5 DUEL HEALTH
----------------------------------------------------------------------

Both finalists start the duel fairly.

Recommended:
- reset both finalists to full 5 hearts
- use the existing health architecture where practical
- visible health for both competitors
- no random cave damage carryover deciding the duel

The duel ends when one finalist reaches zero duel health.

Existing elimination logic may be reused/adapted carefully, but do not accidentally send the duel loser through cave elimination flow.

----------------------------------------------------------------------
6.6 DUEL WEAPON SET
----------------------------------------------------------------------

Do NOT build a large FPS weapon system.

Build a small polished set.

REQUIRED:

A. PULSE BLASTER
- reliable primary attack
- moderate damage
- readable projectile/hitscan
- clear fire cooldown/reload rhythm
- clear VFX/SFX
- no random critical system

B. AXIS LOCK ATTACK
- signature DOF combat weapon/ability
- lower damage and/or longer cooldown
- successful hit temporarily removes one movement freedom from opponent

Examples:
- 3DOF -> 2DOF
- 2DOF -> 1DOF

1DOF duration:
- short
- configurable
- approximately 2–4 seconds is a reasonable starting point

Axis Lock must:
- show what freedom was removed
- show remaining duration
- restore automatically
- have clear sound/visual feedback
- prevent infinite chain-locking using cooldown/immunity as needed

Do not let a player permanently stun-lock the opponent.
