2. REQUEST — NEW MODE: BATTLE TIMER MODE (MULTIPLAYER, KILLS-FOR-SCORE, TIMED)
======================================================================

MODE SELECTION:
- Add "Battle" as a mode choice alongside the existing cave racing rulesets, selectable only for Online or Mixed participation (this mode has no meaningful offline-solo form; if the repository already supports player-vs-bot participation generally, allow bots to fill Battle Mode the same way they fill races — otherwise require at least 2 human-controlled combatants and state that limitation).
- Battle Mode reuses the existing Create Arena/Join by Code flow from Prompt 3: creator picks "Battle" instead of "Normal"/"Rush," configures duration and environment, gets an issued code, friends join that exact lobby, host starts once minimum player rules are satisfied. Do not build a second room/lobby UI.
- Environment selection reuses the existing four themes where the map supports open multi-spawn combat; if an environment's current layout is structurally unsuitable (e.g. a single-path maze with no room for simultaneous distant spawns and skirmishing), state that explicitly rather than silently forcing it to work, and propose the minimal layout addition needed (e.g. designated spawn markers) rather than a new map system.

DURATION:
- Host chooses a fixed match duration. Reuse the existing Rush-style duration pattern (a small fixed set of choices, e.g. 3/5/8 minutes or values consistent with what already exists) rather than inventing a new time-selection UI. Show remaining time clearly, starting at authoritative GO, using the same synchronized-time approach Rush already uses (server/simulation-authoritative time; clients display synced remaining time; freeze host-chosen settings at start).

SPAWNING:
- On match start, distribute all participants across multiple distinct spawn points scattered around the map, not clustered at one shared entrance. Reuse or extend the map's existing spawn-point data if any exists; otherwise define a minimal set of hand-placed or rule-generated spawn markers per environment.
- Avoid spawning two players on top of each other or in immediate line-of-sight/weapon-range of each other at match start. A simple minimum-separation rule between simultaneously-used spawn points is sufficient; this does not need full matchmaking-grade fairness logic.
- On respawn (see below), reuse the same spawn-point pool, again avoiding spawning a just-respawned player next to the player who eliminated them.

COMBAT AND ELIMINATION -> RESPAWN (NOT PERMANENT ELIMINATION):
- Reuse the existing weapon/damage/hit-resolution logic built for the Freedom Duel wherever it is already server-authoritative, adapted to resolve correctly with more than two simultaneous combatants (e.g. no code path that implicitly assumes "the other player" is a single fixed opponent).
- On a player's health reaching zero in Battle Mode: award one point/kill to whoever landed the eliminating hit (if attributable; environmental/self-inflicted deaths do not award a kill to another player, and should be defined explicitly — e.g. no score change, or a small self-penalty, pick one default and document it), then respawn that player after a short, fixed, clearly-displayed respawn delay at a fresh spawn point, restored to full health/starting loadout, with brief spawn protection/invulnerability consistent with how the project already handles spawn/countdown protection elsewhere. This is a hard behavioral difference from cave racing and the Freedom Duel, where zero health currently means elimination/spectating — do not reuse that terminal state machine unmodified for Battle Mode; branch it explicitly into "respawn" behavior for this mode only.
- Battle Mode does not use the cave heart-exchange-for-Moves system (Prompt 3, Request 4) or its last-heart grace/deadline; that system is specific to cave traversal. State this explicitly rather than silently porting it over.
- No qualification, no Freedom Duel transition, and no "Champion" arise from Battle Mode play. If a player leaves/disconnects mid-match, apply the project's existing disconnect handling for arenas (Prompt 3) rather than inventing new duel-style reconnection rules.

SCORING, LIVE STATE AND MATCH END:
- Track each player's kill count (score) authoritatively for the room's duration. Maintain and sync a live scoreboard (name, score, and optionally deaths) visible to all participants during the match, plus a lightweight kill feed ("X eliminated Y") if the UI already has a place for transient match messages; otherwise keep this minimal rather than building new UI infrastructure.
- At timer expiry, the player with the highest score wins. Define and document a deterministic tie-break (e.g. fewest deaths, then earliest to reach the tied score, then declared draw) rather than leaving simultaneous top scores unresolved.
- Resolve match end exactly once using authoritative simulation order, the same way Rush resolves cave expiry in Prompt 3, so that a kill landing at the same instant as the timer running out is handled deterministically and consistently for every client.
- Show a clear results screen: final scores ranked, winner (or declared draw), and an explicit label that this was a Battle Mode result, not a race result and not a duel outcome. Preserve/reuse the existing rematch flow (same room, settings preserved) rather than building a separate one.

NETWORKING AND AUTHORITY:
- All hit resolution, health changes, kill attribution, scoring and the match timer must be authoritative on the server/host in the same way existing combat and Rush timing are authoritative; clients must not independently award kills or score.
- Scope all Battle Mode state (players, spawns, score, timer, kill feed) to its own room/world using the existing room-isolation mechanism (Prompt 3's WorldScope or equivalent). Two concurrent Battle Mode arenas, or a Battle arena running alongside separate racing arenas, must not affect each other.
- Reuse existing debouncing/request-identity patterns to avoid duplicate kill credit or duplicate respawns from repeated/retried RPCs, consistent with how Prompt 3 required this for heart exchange.

ACCEPTANCE:
[ ] A host can create a Battle arena, set duration and environment, and friends join by the existing code flow into that exact lobby.
[ ] All participants spawn at distinct, spread-out locations at match start, not clustered together.
[ ] Landing a lethal hit awards the correct player one point and respawns the eliminated player at a fresh, non-adjacent spawn point after a fixed delay, with brief spawn protection.
[ ] The scoreboard and remaining time stay synchronized and correct across all clients throughout the match.
[ ] No cave heart-exchange, Move economy, qualification or Freedom Duel transition occurs during Battle Mode.
[ ] At expiry, the highest scorer is declared winner, ties resolve per the documented tie-break, and the result is clearly labeled as a Battle Mode outcome.

[ ] Disconnect/leave mid-match is handled per the existing arena disconnect policy without freezing the match for remaining players.
[ ] Existing Normal/Rush cave racing and the existing Freedom Duel remain unchanged and fully playable.

3. REQUEST — SPRINT BECOMES A TIMED PICKUP, NOT A STANDING ABILITY
======================================================================

Observed current behavior: holding Shift grants sprint as an always-available default movement modifier.

Required change:
- Remove Shift-hold-sprint as a standing, always-available part of normal movement. In the default state, pressing or holding Shift MUST NOT increase movement speed at all. Baseline walk/movement speed and feel must otherwise stay exactly as they are today.
- Introduce sprint as a temporary pickup/gift: a world item ("Sprint Gift" or equivalent naming already used in the project's item conventions) that temporarily unlocks the existing Shift-based sprint mechanic for exactly 5 seconds.
- Sprint Gift behavior is explicit:
  - Before collecting/activating a Sprint Gift: Shift does nothing to movement speed; the player moves at normal speed.
  - Immediately after collecting a Sprint Gift: start a 5-second Sprint Gift timer.
  - While that 5-second timer is active, holding Shift makes the player sprint using the project's existing sprint speed/modifier; releasing Shift returns the player to normal speed, but the 5-second gift timer continues counting down.
  - The player may press/release Shift any number of times during the active 5-second window. Sprint is available only while both conditions are true: Sprint Gift timer active AND Shift held.
  - When the 5-second timer expires, sprint access is removed immediately. If Shift is still held at expiry, movement must fall back to normal speed without requiring the player to release/repress Shift.
  - Picking up another Sprint Gift while the timer is already active refreshes the remaining duration back to a full 5 seconds. Durations do not add or stack beyond 5 seconds.
- The Sprint Gift activates immediately on pickup; it is not stored as a separate inventory charge.
- Show clear player-facing feedback for Sprint Gift activation, remaining duration and expiry (e.g. a short on-screen timer/icon), consistent with how other timers in the project are already surfaced (Rush time, last-heart grace).
- KEEP Shift as the sprint input in the existing InputMap/settings system because Shift is still the button used to sprint during an active Sprint Gift. However, update every visible control hint so it does not imply that Shift always provides sprint. The hint should communicate the gated behavior, e.g. "Shift — Sprint (requires Sprint Gift)" or an equivalent concise wording. Active bindings remain the single source of truth for on-screen hints.
- Apply identical sprint-pickup rules to bots: bots must be able to recognize, path to and benefit from Sprint Gifts under the same 5-second availability window. Their sprint decision should only be allowed while their Sprint Gift timer is active.
- This change applies across single-player and multiplayer, and across cave racing and Battle Timer Mode, unless a mode-specific reason is found during inspection to exclude one of them — state any such exclusion explicitly rather than silently applying it everywhere.

ACCEPTANCE:
[ ] Pressing/holding Shift with no active Sprint Gift produces ordinary (non-sprint) movement only.
[ ] Collecting a Sprint Gift immediately opens an exactly 5-second sprint-access window.
[ ] During that window, holding Shift sprints; releasing Shift returns to normal movement while the gift timer continues.
[ ] The player can press/release Shift repeatedly during the same active window without resetting or pausing the timer.
[ ] At exactly timer expiry, Shift stops granting sprint immediately, even if Shift is still being held.
[ ] Collecting another Sprint Gift while one is active refreshes the window to 5 seconds and never stacks above 5 seconds.
[ ] The UI clearly indicates Sprint Gift active state and remaining duration.
[ ] Control hints clearly state that Shift sprint requires an active Sprint Gift.
[ ] Bots only sprint while their own Sprint Gift window is active, under the same 5-second rule.
[ ] The change is applied consistently across the modes it is meant to affect, with any exclusions stated.

4. REQUEST — INCREASE CAVE COMPLEXITY AND MINIMUM COMPLETION TIME
======================================================================

Observed problem: caves are finished far too quickly under real play — the Hard/Normal-difficulty cave is being finished in under 1 minute, and the Easy-difficulty cave in under 30 seconds. This is too short for the intended exploration experience.

Target (confirmed by the user):
- Easy-difficulty caves must take at least 1 minute 30 seconds (90 seconds) to complete under ordinary, non-omniscient play, across a representative sample of seeds — not merely on average, but as a lower bound most seeds should meet.
- The user has not specified an exact floor for harder difficulties. As a design default, scale the completion-time floor upward for harder tiers relative to Easy's 90-second floor (e.g. each tier meaningfully longer than the one below it), preserving the existing relative difficulty ordering. Document this scaling explicitly as an inferred default pending user confirmation, rather than presenting it as a stated requirement.
- This complexity/time increase must not violate Prompt 3's requirement that Rush remain measurably easier to navigate than Normal at a comparable size — if Easy in this request corresponds to Rush, raise its floor while preserving that relative gap; state clearly if "Easy" here refers to a different existing tier.

CAVE STRUCTURE — DEAD ENDS AND "LONG CUT" DECEPTIVE ROUTES:
- Increase dead-end density generally: more branching paths that terminate without reaching the destination, requiring the player to notice the mistake and backtrack.
- In addition to true dead ends, introduce "long cut" branches: a wrong turn that does not dead-end abruptly but instead loops back and rejoins the correct critical path much further along, after a materially longer detour. The player is not blocked or forced to backtrack to their exact entry point — they keep moving, but toward a much longer route to the same destination. This should read as a deceptive detour, not a broken/unfair path.
- Use a documented mix of both patterns (true dead ends vs long-cut rejoins) per difficulty, tunable independently, rather than only one or the other. Harder difficulties may lean more on costly true dead ends; easier difficulties may lean more on long-cut detours so newer players are slowed down without feeling punished by hard backtracking.
- Preserve every existing generation guarantee from Prompt 1/3: deterministic generation from seed, gravity-aware solvability, and solvability without requiring random loot or heart sacrifice. Long-cut and additional dead-end branches must still resolve to a genuinely solvable cave, validated the same way existing generation is validated.
- Extend the existing seed-testing/metrics suite (Prompt 3, "COMPLEXITY AND DETERMINISM": branch/dead-end counts, detour depth, route length, required shifts, physical exploration time) to also report and enforce a minimum solvable-path-length / minimum expected completion-time floor per difficulty at generation-validation time. Reject or regenerate seeds that fall under a difficulty's floor rather than relying only on average-case tuning.

FURTHER SUGGESTIONS TO INCREASE TIME-ON-TASK (OPTIONAL — FOR CONSIDERATION, NOT ALL MANDATORY):
Present the following as concrete options; implement the ones the user selects, and clearly list which were implemented, which were considered and skipped, and why:
1. Raise the minimum number of gravity shifts required along the critical path, forcing more orientation changes and Move spending, since each shift already costs time and a Move.
2. Add occasional "false destination" visual/audio cues (decor, light, sound) visible from a distance that turn out to lead nowhere, tempting players off the true route before they learn to distinguish real cues from decoys.
3. Require at least one non-trivial vertical (floor-to-ceiling or multi-face) detour along the critical path per cave, rather than allowing a mostly-flat critical route.
4. Reduce visibility range/lighting radius so distant objectives or landmarks are not visible early, discouraging players from beelining based on landmark spotting rather than actual exploration.
5. Add small, clearly optional side-objectives (existing boxes/clues) positioned off the fastest route, so players who choose to collect them naturally spend more time, without making them mandatory for completion or penalizing players who skip them.
6. If repeated play on the same seed is a suspected shortcut (players memorizing a known-fast route), consider whether decorative/non-structural landmark variation across regenerations is warranted — flag this as a hypothesis to verify with real player data before investing in it, not a confirmed requirement.

ACCEPTANCE:
[ ] Across a representative sample of seeds, Easy-difficulty caves take at least 90 seconds to complete under ordinary non-omniscient play, not just on average.
[ ] Harder difficulties retain a documented, proportionally larger completion-time floor than Easy, per the stated default scaling.
[ ] Rush remains measurably easier to navigate than Normal at comparable size, per Prompt 3, even as absolute time floors rise.
[ ] Generation remains deterministic, gravity-aware and solvable without random loot or heart sacrifice.
[ ] Wrong turns include a documented, tunable mix of true dead ends and long-cut branches that rejoin the critical path later.
[ ] The seed-testing/metrics suite enforces and reports the new minimum path-length/time floors at generation-validation time, rejecting/regenerating seeds that fall short.
[ ] Each optional suggestion above is explicitly marked implemented, deferred, or rejected, with a one-line reason.
