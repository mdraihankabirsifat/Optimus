2. Original game concept

The project begins with two or more robots/players who possess unequal degrees of freedom. Their movement controller must mechanically reject illegal motion rather than relying only on instructions or visual storytelling.

DOFAllowed abilityMeaning in the prototype
1 DOFTranslate along X axisMove left and right only.
2 DOFTranslate along X and Y axesAdd upward/downward movement.
3 DOFX/Y translation plus rotationCan also rotate around its own axis.

Still intentionally undecided

The team has not yet fixed what players ultimately do. Possibilities discussed were fighting one another or cooperating/competing to achieve an objective. The present energy-collection and hazard loop is a neutral mechanic test, not the promised final design.

Design requirement: the eventual goal must make all DOF roles valuable. If more DOF is simply always better, the mechanic becomes an ordinary upgrade system instead of meaningful asymmetry.

Recommended creative north star

Build around interdependence or trade-offs: the restricted player should gain a compensating power, safety, precision, or access that the freer player lacks. A judge should be able to say, “Their movement limitations create the strategy,” after watching for thirty seconds.

3. Development approach discussed

  • The team intends to “vibe code.” Godot is suitable for this because scenes and GDScript are text-based and can be edited by coding agents, but every change must still be run and tested inside Godot.
  • Godot was chosen over plain JavaScript because the project needs game-centric scenes, input handling, audio, collision/physics, UI, export, and future multiplayer structure under a short deadline.
  • Use GDScript, not C#, for speed and simpler Godot integration. The final installed build is Godot Standard rather than Mono.
  • Cost-conscious model plan: use Sol Medium for broad skeleton/mechanical work, then Astra Medium for complex architecture, important gameplay, networking, debugging, and polish. Astra High should be reserved for genuinely difficult failures or a final deep review, not routine edits.
  • Every AI coding prompt should request inspection first, bounded changes, preservation of existing files, validation, and a concise report of changed files.

Present local gameplay behavior

  • Player 1 initially spawns with 1 DOF; Player 2 initially spawns with 2 DOF.
  • Each collected energy node awards 10 points and respawns shortly afterward at a random arena position.
  • Hazard damage depends on difficulty. Reaching zero health ends the game with “ROBOT DISABLED.”
  • Timer expiry ends the test successfully with “TEST WINDOW COMPLETE.”
  • Team score is Player 1 score + Player 2 score. Successful completion can record a new high score and unlock progression.

7. Hosted multiplayer target

The end goal is a hosted two-player game playable from different devices. Phase 1 deliberately remains local so movement feel, menus, scoring, saving, and the core DOF rule can be tested without simultaneously debugging latency, NAT, rooms, synchronization, deployment, and identity.

Current boundary

NetworkManager exposes connection/disconnection/failure concepts, but calls currently return the message: Hosted networking is not implemented in Phase 1. This is honest scaffolding, not a partially working network layer.

Proposed Phase 2 architecture

  • Use a publicly reachable, WebSocket-compatible dedicated authoritative server so both Windows and Web clients share a transport.
  • Clients send input intent. The server validates each movement against the player’s DOF and owns authoritative position/rotation, health, score, timer, collectibles, and hazards.
  • Add room creation/joining with short codes, player identity, ready state, disconnect/reconnect, and protocol version checking.
  • Broadcast snapshots and use interpolation/reconciliation to keep client movement responsive.
  • Keep deployment URLs, tokens, secrets, and paid-service configuration outside the repository.
Important scope warning: hosted multiplayer is the largest technical risk. Do not begin it before locking the final game loop and proving it locally. If time becomes unsafe, a polished local multiplayer submission is better than a broken online claim, unless the official requirement explicitly mandates online play.

8. Recommended execution roadmap

  1. Lock the final loop. Decide combat vs cooperative objective vs competitive objective. Define a one-sentence win condition and why each DOF role matters.
  2. Build one complete arena. One level should contain the full loop, readable feedback, win/lose state, restart, and satisfying moment-to-moment play.
  3. Balance asymmetric roles. Give lower-DOF robots unique value rather than treating them as weaker versions.
  4. Replace placeholder presentation. Add a distinctive name, robot identity, coherent visual theme, sound effects, music, particles, hit/pickup feedback, and a brief tutorial.
  5. Test local multiplayer heavily. Verify every allowed/forbidden input, collisions, scores, health, timer, pause, level transitions, and saves.
  6. Add online networking only after the loop is stable. Start with two clients joining a room and synchronized movement, then authority and game state.
  7. Export early. Produce and test both Windows and Web candidates on machines other than the developer laptop.
  8. Submission package. Prepare itch.io page, gameplay video, screenshots, controls, credits/AI disclosure, technical notes, exact commit/build, and demo laptop.

9. Decisions still required

  1. Final game name: team name is Optimus; “Project DOF” is only the current working name.
  2. Core loop: fight, race, cooperative puzzle, extraction, asymmetric objective, or another mechanic.
  3. Relationship: pure PvP, pure co-op, or competitive co-op.
  4. DOF assignment: fixed roles, random roles, selectable roles, or dynamically changing DOF.
  5. Compensation: what special advantage makes a 1-DOF player strategically valuable?
  6. Win condition and round length: must be explainable immediately and demo well.
  7. Online scope: room codes only, matchmaking, local fallback, reconnect behavior.
  8. Hosting choice: provider, server runtime, deployment plan, cost/free-tier limits, and WebSocket support.
  9. Submission target: Windows, Web, or both. Both are ideal only if both remain stable.
  10. Credits and disclosure: final member list, third-party assets/licenses, AI-assisted work disclosure.

10. Verification and submission checklist

Technical QA

  • Fresh clone imports without missing resources.
  • Smoke test prints PHASE1_SMOKE_OK.
  • F5 opens the correct main scene.
  • All menu buttons and keyboard focus work.
  • 1/2/3 DOF restrictions are enforced.
  • Two-player controls do not conflict.
  • Settings and scores survive restart.
  • Windows and Web exports run on other devices.
  • No personal paths, secrets, or generated build caches are committed.

Judge-facing QA

  • Theme connection is visible without explanation.
  • Tutorial/controls take under 30 seconds.
  • The first fun decision appears quickly.
  • Roles are visually distinguishable.
  • Audio and feedback communicate important actions.
  • A full round fits the demo time.
  • The demo works without relying on venue internet, or has a safe fallback.
  • The team has a concise 60–90 second pitch.
